# Feature requests (Alexa+ add-ons, MCP Apps, Ring Partner API)

Format per the hackathon rules: description · why it matters to this project · priority (Critical / Important / Nice-to-have). Each links to the friction-log entry or the place in our code that works around it.

| # | Request | Why it matters to Proof Before Pay | Priority | Link |
|---|---|---|---|---|
| R1 | Let an add-on complete part of an amount in checkout: either several checkout sessions per booking (documented), or a partial-capture concept on one session, with the remainder visibly pending. | Our whole value is "pay the proven part now, the rest after you confirm". Today Alexa+ checkout sessions are immutable after completion and have no partial concept, so we model the waiting part as a second session — a design inference we could not confirm in the docs. | Critical | SPEC §7.1; research `critic.md` §1.3 |
| R2 | Document one supported way to combine Browse-and-Choose discovery (`ListProfessionals`) with a booking stage (`CreateBooking` ESTIMATE → CONFIRMATION) for the same service. | Homeowners choose the licensed pro themselves, then need an estimate with policies and a confirmed booking. The SPI documents these operations for mutually exclusive patterns, so our flow has to be labelled "our combination". | Important | SPEC §7.2; `home-services-spi.txt:125-136, :180` |
| R3 | Add a verified-credential field to `Professional` (license number, issuing registry, status, as-of date) next to free-text badges such as "Licensed Contractor". | A badge string is not a check. A structured field would let add-ons and Alexa itself show "license active per the state registry, as of …" with a source. | Important | `src/core/registry/`; SPEC §1 beat 1 |
| R4 | Put a scale hint (device class root scale, e.g. 1.667 for Echo Show 8/15) into the MCP Apps `hostContext`, or document that the host scales the view. | The Alexa+ design guide asks for one root scale per device; MCP Apps gives the view no scale signal, so our cards fit themselves. | Important | FRICTION-LOG #4 |
| R5 | Publish the dual-era (2025-11-25 sessions + 2026-07-28) serving pattern of the TypeScript SDK v2 in the docs, not only in type comments, and list 2026-07-28 in the SDK version constants. | We serve both eras from one endpoint; finding how took reading type definitions. | Nice-to-have | FRICTION-LOG #1, #2 |
| R6 | Ring Partner API: an access-control capability for partner apps (time-boxed door codes on supported locks), or document that none is planned. | The one-day door code for the visit is simulated today; "access control" is listed in Ring's priorities, but there is no API for it. | Important | FRICTION-LOG #7 |
| R7 | Ring Developer Playground without full developer registration (read-only sandbox with simulated events), or a public JSON fixture set for webhooks v1.1. | Testing our webhook receiver against real Playground events needs an Amazon Developer registration first; we built against the documented payloads instead. | Nice-to-have | `src/core/doorbell/ring-format.ts` |
| R8 | Ship MCP Apps' `App` view helper without bundling all of zod (or tree-shakeable schemas). | Each card is ~612 KB, 442 KB of it zod; Alexa+ guidance asks for small, cached payloads. | Nice-to-have | FRICTION-LOG #3 |
